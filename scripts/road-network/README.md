# 道路ネットワーク距離のオフライン事前計算パイプライン

`feature/road-network-distance` ブランチで検証中。藤沢市（丹野氏）からの「直線距離ではなく道路ネットワーク上の経路距離で交通空白地を判定すべきでは」という提案の実装。**まだ`app/PlateauViewer.tsx`には組み込んでいない**（下記「結論」参照）。

## 実行方法

```bash
cd scripts/road-network
python3 -m venv venv && source venv/bin/activate
pip install osmnx scikit-learn

python3 01_fetch_buildings.py       # 藤沢市の建物3D Tiles（697タイル）を再帰的にダウンロード・パースし、
                                     # 住宅系×北部の建物一覧をbuildings.jsonに書き出す（約78,542件）
python3 02_fetch_road_network.py    # osmnxで歩行可能な道路網を取得し road_network.graphml に保存
python3 03_compute_scores.py        # 本体。上記2つ＋既存のbus-stops.json/train-stations.jsonを使い、
                                     # public/data/building-network-scores.json を生成する
                                     # （--limit N でデバッグ用に件数制限、--buildings-file/--outputで
                                     #   入出力パスを差し替え可能）
python3 compare_straight_vs_network.py --full  # 直線距離版との比較レポートを表示
```

## 手法

1. **建物データ**: `app/PlateauViewer.tsx`がクライアント側でCesium3DTileFeature.getProperty()経由で読んでいるのと同じデータを、`.b3dm`のバッチテーブルバイナリを直接パースして取得（AGENTS.mdに記載の「実際に.b3dmをPythonでパース済み」という過去の検証を実際に再現・スクリプト化したもの）
2. **道路網**: `osmnx`で`network_type='walk'`・`simplify=False`（理由は後述）
3. **スナップ**: 建物・バス停・駅をそれぞれ最寄りの道路網**ノード**にスナップ（エッジへの投影ではなくノードへのスナップ。理由は下記「簡略化した点」参照）
4. **経路探索**: バス停・駅それぞれに仮想スーパーソースノードを追加し、1回のダイクストラ法で「建物ごとの真にネットワーク上最も近い停留所」までの最短経路・距離を一括計算（直線距離で決め打ちした最寄り駅に対して経路探索するのではなく、ネットワーク上で本当に最も近い停留所を探している）
5. **標高**: 国土地理院の標高タイルAPI（`https://cyberjapandata.gsi.go.jp/xyz/dem5a/{z}/{x}/{y}.txt`、5mメッシュ、z=15）をタイル単位でキャッシュしながら取得。XMLメッシュ配布形式より簡単に扱える
6. **実効距離**: 経路上の各ノード＋建物・停留所の実座標を頂点列とし、既存アプリと全く同じ計算式（区間距離×(1+係数×min(勾配,0.4))）で積み上げる。「一般」「高齢者」両プロファイルぶん計算し、既存の`app/PlateauViewer.tsx`のプロファイル切り替え機能をそのまま維持できるようにしている

## ハマった点（実装時に遭遇したバグ）

1. **`simplify=True`だと勾配が過大評価される**: 簡略化されたエッジの`length`属性（実際の道のり長、曲線込み）と、勾配計算に使うノード間の直線距離が食い違い、実効距離が理論上限（1+係数×0.4倍）を超えてしまう不具合が発生した。→ `simplify=False`に変更して解消（グラフは161,780ノードに増えるが、ダイクストラは1回の走査で済むため計算量的には問題なし）
2. **同名バス停の取り違え**: 「住宅前」など、藤沢市内に同名だが全く別の場所にあるバス停が複数存在する（`住宅前`3箇所、`三富士町`/`公民館前`/`日本精工前`各2箇所）。当初、経路探索後に停留所の実座標を「名前で元データから再検索」していたところ、同名の別の（時に数km離れた）停留所を誤って拾ってしまい、実効距離が数千mに跳ね上がるバグがあった。→ スーパーソース構築時点で停留所の実座標を直接保持するよう修正し、名前での再検索を廃止して解消

## 結論・比較結果（78,542件全件、2026-08-24時点）

| 指標 | 直線距離ベース（既存） | 道路網距離ベース（本ブランチ） |
| --- | --- | --- |
| 建物カバー率（一般プロファイル） | 76.7% | **48.1%** |
| 建物カバー率（高齢者プロファイル） | （app未実装だった時点の比較なし） | **43.5%** |
| 藤沢市公式資料（市全域） | 78% | 78% |

**道路網ベースにすると、公式資料の数値（78%）からの乖離はむしろ拡大した**（直線距離ベースは76.7%とほぼ一致していたのに対し、道路網ベースは48.1%と約30ポイント低い）。

個別の建物の経路を検証したところ、道路網ベースの経路自体は妥当（丘陵地を迂回する等、現実の道路をたどっている）ことを確認済みで、バグではなく実際の街路網の構造を反映した結果と考えられる。ただし、いくつかの建物では停留所までわずか15〜50m（直線距離）しか離れていないのに道路網距離が400〜800mに達するケース（detour factor 15〜32倍）も見つかっており、これはノードへのスナップ（エッジへの厳密な投影ではない、簡略化した点）に起因する可能性がある局所的な精度の限界として残っている。

**解釈**: この結果は「道路網ベースが不正確」というよりも、**藤沢市公式資料の78%という数値自体が、恐らく直線距離（円形バッファ等の簡易GIS手法）で算出されている**可能性を強く示唆している。道路網ベースの48.1%は、実際の徒歩アクセシビリティとしてはむしろ直線距離版より正直な数値である可能性が高いが、「公式資料の数値に近づく」というユーザー側の判定基準には合致しなかった。

以上を踏まえ、**mainブランチへのマージは保留**し、ユーザーの判断を仰いでいる（詳細な指示に「明らかに改善していなければ現状維持でも構わない」とあったため）。

## 既知の制約・今後の課題

- **`public/data/building-network-scores.json`が44.5MB（gzip後約4.8MB）と大きい**。まだクライアント側への組み込みはしていないが、組み込む場合はフィールドの間引き（`coverageRatio`/`isCovered`はクライアント側で実効距離から再計算すれば冗長）や配列形式の見直し（オブジェクトの配列だとフィールド名が78,542回繰り返されるのが主な肥大化要因）が必要
- ノードスナップ（エッジ投影ではない）に起因すると見られる少数の高detour factorケースが残っている。エッジへの厳密な投影に切り替えれば改善する可能性がある
- 高齢者プロファイルの係数（`SLOPE_PENALTY_FACTOR`等）は既存アプリと同じ目安の値をそのまま使っており、道路網ベース特有の再検証はしていない
